# flow-pair — 블로그 글 페어 파이프라인

블로그 글 한 편을 작성자와 함께 기획부터 게시까지 끌고 간다.
이 스킬이 주로 보는 것은 **문장 표면이 아니라 논리의 이음매**다. 문장이 매끄러워도 A 다음에 B 없이 C 가 나오면 독자는 길을 잃는다.
그리고 **혼자 다 고치지 않는다.** 글의 의도는 작성자 머릿속에 있으므로, 한 곳씩 짚고 묻고 작성자가 고른 것만 고친다.

> 이 스킬의 단계 구조와 검토 기준은 `clyderankin/essay-skills`(README 에 MIT 로 표기)의 에세이 파이프라인을 참고해 한국어 블로그에 맞게 새로 썼다.

## 기준 문서

- 문체·글의 구성·글쓰기 원칙·frontmatter·파일 위치는 레포 루트 `CLAUDE.md` 가 정본이다. 이 스킬은 그 규칙을 다시 적지 않고 절 이름으로 가리킨다.
  - 「글 작성 기준 (`_posts/`)」: 위치·파일명·frontmatter·제목 단계·영어판
  - 「글쓰기 원칙」: 판정 말투 금지, 지어낸 일화 금지, 맥락 유지, 사실 확인
  - 「문체」: 합니다체 기준과 기준 글
  - 「글의 구성 (기존 글에서 보이는 것)」: 도입·강조·표·사례·맺음
- 목소리 샘플은 따로 받지 않는다. 「문체」 절이 고른 기준 글이 그 역할을 한다.

## 단계

| 단계 | 파일 | 하는 일 | 남기는 것 |
|---|---|---|---|
| 1. 기획 | `steps/1-brief.md` | 질문으로 글의 핵심 주장·독자·갈래·사례를 받는다 | `brief.md` |
| 2. 개요 | `steps/2-outline.md` | 구간과 관통선을 설계하고 구조 위험을 짚는다 | `outline.md` |
| 3. 초안 | `steps/3-draft.md` | `_posts/` 에 한국어판 초안을 쓴다 | 글 파일 |
| 4. 고치기 | `steps/4-revise.md` | 한 곳씩 의도를 묻고 방안을 내서 고친다 | 글 파일 수정 |
| 5. 검토 | `steps/5-review.md` | 다섯 축으로 진단하고 출간 판정을 낸다 | `review.md` |
| 6. 다듬기 | `steps/6-polish.md` | 리듬·낱말을 다듬고 humanize-korean 을 부르고 솔직한 평가를 낸다 | 글 파일 수정 |
| 7. 게시 | `steps/7-publish.md` | 영어판을 만들고 형식 검사 후 PR 을 연다 | 영어판, PR |

흐름 점검 기준표는 `flow-checks.md` 에 있다. 고치기·검토 단계와 `flow-diagnostician` 에이전트가 함께 쓴다.

## 시작할 때

1. 대상 글이 무엇인지 정한다. 새 글이면 파일명용 짧은 이름(`YYYY-MM-DD-영문-이름`)을 작성자와 정한다. 이미 있는 글이면 그 파일명을 쓴다.
2. 작업 폴더 `_workspace/flow-pair/<파일명에서 .md 를 뺀 것>/` 에 `brief.md`·`outline.md`·`review.md` 가 있는지, `_posts/` 에 글 파일이 있는지 본다.
3. 있는 것에 맞춰 다음 단계를 권한다. 작성자가 단계를 고르면 그 단계로 간다. 순서는 권장일 뿐이라 건너뛰거나 다시 돌려도 된다.
   - 아무것도 없음: 기획부터. 이미 메모가 있으면 붙여 달라고 한다.
   - 기획만 있음: 개요(권장) 또는 초안.
   - 글이 있음: 고치기 / 검토 / 다듬기(검토에서 「바로 다듬기 가능」이 나온 뒤 권장).
   - 기존 글만 다듬고 싶다는 요청("흐름 봐줘" 등): 기획 없이 검토 또는 고치기로 바로 간다.
4. 고른 단계 파일을 읽고 그대로 따른다. 단계가 끝나면 다음 단계를 한 줄로 권한다.

## 기획 자료는 어디에 두나

- **작업본은 `_workspace/flow-pair/<글 이름>/` 에 둔다.**
  - `_workspace/` 는 `.gitignore` 에 있어 커밋되지 않는다. 밑줄로 시작하는 폴더라 Jekyll 도 사이트에 내지 않는다(`_config.yml` 의 `include`·`collections` 에 없음).
  - humanize-korean 도 `_workspace/YYYY-MM-DD-NNN-TAG/` 를 쓴다. 그쪽은 날짜로 시작하는 폴더만 훑으므로 `flow-pair/` 하위 폴더와 겹치지 않는다.
- **한계:** 워크트리 안의 `_workspace/` 는 워크트리를 지우면 같이 사라진다. 그래서 게시 단계에서 `brief.md`·`outline.md` 요지와 마지막 `review.md` 를 PR 본문에 옮긴다. 기록은 PR 이 맡는다.
- 다른 세션에서 이어 쓸 때 작업본이 없으면, 그 글의 PR 본문이나 작성자에게 기획 요지를 받아 `brief.md` 를 다시 만든다.

## 철칙

1. **작성자의 주장과 사례만 쓴다.** 빈 곳을 메울 때도 글에 이미 있는 주장, 또는 작성자가 대화에서 직접 말한 내용만 엮는다. 새 주장·새 예시·지어낸 1인칭 일화를 넣지 않는다. 사례가 필요한데 없으면 지어내지 말고 `[?? 사례 필요: 무엇을 물을지]` 로 비워 둔다.
2. **의도를 짐작해야 하면 묻는다.** "제가 짐작한 의도는 이렇다"를 한 문장으로 밝히고, 맞는지 확인받은 뒤 쓴다.
3. **한 번에 한 곳.** 문제 목록은 한꺼번에 보여 주되, 고치는 건 작성자가 고른 곳부터 하나씩 한다.
4. **판정하지 않고 설명한다.** 검토는 솔직하게 하되 "틀렸다/엉망이다" 대신 독자가 거기서 무엇을 겪는지와 왜 그런지를 말한다. 출간 판정 네 가지는 글의 상태를 말하는 것이지 작성자를 평가하는 말이 아니다.
5. **고치는 방법은 하나가 아니다.** 다리 넣기만 답이 아니다. 순서 바꾸기, 구간 통째로 빼기, 표의 행 이름 바꾸기도 후보로 함께 낸다.
6. **`CLAUDE.md` 가 외부 관례보다 우선한다.** 예를 들어 줄 첫머리 「그래서」는 기준 문체의 일부이므로 기계적 접속어로 보고 지우지 않는다.

## 말투

- 작성자에게는 한국어 대화체로, 결론(어디가 왜 끊기는지, 판정이 무엇인지)부터 말한다.
- 제안 문장 초안은 그 글의 문체(합니다체, 또는 해라체로 쓴 기존 철학 글이면 해라체)를 그대로 따른다.
- 목록은 마크다운 `-`·`1.` 을 쓴다. `•`, `—` 는 블로그 글에 넣지 않는다.
