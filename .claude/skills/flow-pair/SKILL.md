# flow-pair — 글 흐름 점검과 페어 다듬기

이 스킬은 **문장 표면이 아니라 논리의 이음매**를 본다. 문장이 매끄러워도 A 다음에 B 없이 C가 나오면 독자는 길을 잃는다.
그리고 **혼자 다 고치지 않는다.** 글의 의도는 작성자 머릿속에 있으므로, 한 곳씩 짚고 묻고 고른 것만 고친다.

> 역할 나눔
> - **flow-pair (이 스킬)**: 구간·문단 사이의 흐름, 인과, 맥락, 주어, 구성
> - **humanize-korean**: 문장 안의 AI 티(번역투, 쉼표, 관용구)
> - **`python3 tools/check_posts.py`**: frontmatter·제목 단계 같은 형식

## 철칙

1. **작성자의 주장과 예시만 쓴다.** 빠진 다리를 메울 때도 글에 이미 있는 주장, 또는 작성자가 대화에서 직접 말한 내용만 엮는다. 새 주장·새 예시·지어낸 1인칭 일화를 넣지 않는다.
2. **의도를 짐작해야 하면 묻는다.** "제가 짐작한 의도는 이렇다"를 한 문장으로 밝히고, 맞는지 확인받은 뒤 쓴다. 짐작으로 쓴 다리는 작성자 의도와 어긋나 몇 번씩 다시 쓰게 된다.
3. **한 번에 한 곳.** 문제 목록은 처음에 한꺼번에 보여 주되, 고치는 건 작성자가 고른 곳부터 하나씩 한다.
4. **판정하지 않고 설명한다.** "틀렸다/맞았다/흔한 실수" 대신 "독자가 여기서 무엇을 모른 채 넘어가는지"를 말한다. 레포 `CLAUDE.md` 의 블로그 글쓰기 원칙을 그대로 따른다.
5. **고치는 방법은 하나가 아니다.** 다리 넣기만 답이 아니다. 순서 바꾸기, 구간 통째로 빼기, 표의 행 이름 바꾸기도 후보로 함께 낸다.

## 진행 순서

### 1. 글 읽기와 진단

- 대상 글(`_posts/...` 한국어판)을 끝까지 읽는다. 영어판이 있으면 위치만 확인해 둔다.
- 글이 길거나 작성자와 같은 관점에 묶이지 않은 첫 읽기가 필요하면 `flow-diagnostician` 에이전트에 진단을 맡긴다(없으면 general-purpose 에이전트에게 `.claude/agents/flow-diagnostician.md` 를 읽혀 돌린다). 짧은 글은 직접 진단한다.
- 아래 **점검 항목**으로 끊기는 곳을 찾는다.

### 2. 글의 뼈대 보여 주기

먼저 글이 지금 어떤 순서로 흘러가는지 번호 목록 한 줄씩으로 보여 준다(구간별 "무엇을 말하는가"). 작성자가 자기 글의 뼈대를 보면 끊기는 곳을 스스로 먼저 찾기도 한다.

### 3. 끊기는 곳 목록

곳마다 이 세 줄로 쓴다. 심한 순서로 3~6개까지만.

```
N. [위치: 소제목 / 문단 첫 구절]
   독자가 겪는 일: 무엇이 갑자기 나오는지, 무엇을 모른 채 넘어가는지
   원인: 빠진 다리 / 늦게 나온 개념 / 주어 모호 / 구간 순서 / 압축 과다 ...
```

글을 앞서 고친 적이 있으면 **원문부터 있던 문제인지, 고치면서 생긴 문제인지**도 적는다(`git log -p -- <파일>` 로 확인).

### 4. 한 곳씩 페어

작성자가 고른 곳(지정이 없으면 1번)부터:

1. **의도 확인**: "여기서 하려던 말이 ~인가요?"를 짐작과 함께 묻는다. 의도가 글에 이미 분명하면 생략한다.
2. **방안 2~3개**: 다리 문장 넣기 / 순서 바꾸기 / 구간 빼기 / 풀어 쓰기 등. 각 방안에 실제로 들어갈 문장 초안을 붙이고, 하나를 추천한다.
3. **작성자가 고르거나 고쳐 준 대로** 반영한다. 작성자가 자기 말로 의도를 풀어 주면 그 표현과 예시를 최대한 그대로 살린다.
4. **고친 뒤 앞뒤 다시 읽기**: 아래 "고친 뒤 확인"을 돈다.
5. 다음 곳으로 넘어갈지 묻는다.

### 5. 마무리와 게시

작성자가 "됐다"고 하면:

1. 영어판(`_posts/en/...`)을 한국어판과 같은 흐름으로 맞춘다.
2. 바뀐 문단을 **humanize-korean** 으로 검토한다.
3. `python3 tools/check_posts.py` 위반 0건을 확인한다.
4. PR을 올리고 바로 머지, 배포된 페이지에서 바뀐 문단을 확인한다(이 블로그는 묻지 않고 머지까지 한다).

작은 수정을 곳마다 바로 배포해 달라고 하면 4번을 곳마다 돈다.

## 점검 항목

| 항목 | 보는 것 | 예 |
|------|---------|-----|
| **빠진 다리** | A 다음에 C가 나오는데 A→C를 잇는 B(어떻게, 왜)가 없다 | "마찰이 있다" → "AI 덕에 매끄럽다". AI가 *어떻게* 마찰을 없애는지가 없다 |
| **갑자기 나오는 개념** | 앞에서 한 번도 깔지 않은 용어·틀이 결론부에 처음 나온다 | 기질 충돌만 말하다가 끝에서 "과거의 How 전장"이 처음 나온다 |
| **주어·소유 모호** | 누구의 고민·행동인지가 흐려진다. 표로 묶을 때 특히 잘 생긴다 | How는 개발자의 질문인데 표에서 공동의 질문처럼 읽힌다 |
| **결론에서 감정으로 점프** | 논리적 결론 뒤에 "나"의 감정·장면이 이어 주는 자각 없이 나온다 | 지휘자 결론 → 터미널 앞의 찝찝함 |
| **흐름 밖 구간** | 앞뒤 논지 어디에도 기대지 않는 구간. 다리보다 빼는 게 나을 수 있다 | |
| **압축 과다** | 다리가 있긴 한데 한두 문장이라 작성자가 말하려던 뉘앙스가 안 산다 | 작성자 말: "다리 문단이 너무 생략됐다" |
| **엉뚱하게 읽힘** | 문장이 작성자 의도와 다른 결론으로 읽힐 수 있다 | "개발자가 건드릴 게 없다" → "개발자는 할 일이 없다"로 읽힌다 |
| **선언만 있고 과정 없음** | "~로 옮겨 간다"고 말만 하고 옮겨 가는 장면·예시가 없다 | "What·Why로 옮겨 간다"만 있고 그 질문을 주고받는 장면이 없다 |
| **리듬 단조** | 같은 길이 문단 연속, 소제목 하나, 전환 질문이 본문에 묻힘 | 소제목 나누기, 전환 질문 인용 블록, 핵심 문장 한 줄 문단 |

## 고친 뒤 확인

- **떠도는 지시어**: 뺀 구간을 가리키던 "그 찝찝함", "앞서 말한" 같은 말이 남지 않았는가
- **되풀이**: 새로 넣은 다리와 바로 뒤 문장이 같은 말을 반복하지 않는가
- **표와 본문 일치**: 표의 행 이름·칸이 본문 논지와 같은 말을 하는가
- **소제목**: 구간이 바뀌었으면 소제목과 목차도 그 내용에 맞는가
- **영어판**: 한국어판과 같은 순서·같은 주장인가

## 말투

- 작성자에게는 한국어 대화체로, 결론(어디가 왜 끊기는지)부터 말한다.
- 제안 문장 초안은 글 본문의 말투(~다 / ~습니다)를 그대로 따른다.
- 목록은 마크다운 `-`·`1.` 을 쓴다. `•`, `—` 는 블로그 글에 넣지 않는다.
