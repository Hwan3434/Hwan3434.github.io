# 4단계: 고치기

고쳐 쓰는 사람이 아니라 고치기를 함께하는 짝이다. 작성자는 무엇을 말하고 싶은지 안다. 이 단계는 그것을 더 잘 말하게 돕는다. 통째로 다시 쓰지 않고 한 곳씩 정밀하게 고친다.

## 준비

- `brief.md` 가 있으면 먼저 읽는다. 모든 수정이 기획서의 주장·제약을 지켜야 한다.
- 대상 글을 끝까지 읽는다.
- 고칠 곳을 정한다. 출처는 셋 중 하나다.
  - 작성자가 짚은 곳과 메모
  - 5단계 검토의 「반드시 고칠 것」·「고치면 좋은 것」
  - 초안의 `[?? …]` 표시
- 출처가 없으면 `flow-checks.md` 로 끊기는 곳을 찾는다. 글이 길거나 작성자와 같은 관점에 묶이지 않은 첫 읽기가 필요하면 `flow-diagnostician` 에이전트에 맡긴다(없으면 general-purpose 에이전트에게 `.claude/agents/flow-diagnostician.md` 를 읽혀 돌린다).

## 글의 뼈대와 끊기는 곳 보여 주기

고칠 곳이 여럿이면 먼저 보여 준다.

1. 글이 지금 흐르는 순서를 구간별 한 줄씩 번호 목록으로 보여 준다. 작성자가 뼈대를 보면 끊기는 곳을 스스로 먼저 찾기도 한다.
2. 끊기는 곳을 심한 순서로 3~6개, 곳마다 세 줄로 쓴다.

```
N. [위치: 소제목 / 문단 첫 구절]
   독자가 겪는 일: 무엇이 갑자기 나오는지, 무엇을 모른 채 넘어가는지
   원인: flow-checks.md 의 항목 이름
```

글을 앞서 고친 적이 있으면 **원문부터 있던 문제인지, 고치면서 생긴 문제인지**도 적는다(`git log -p -- <파일>` 로 확인).

## 한 곳씩 페어

작성자가 고른 곳(지정이 없으면 1번)부터 한다.

1. **의도 확인**: "여기서 하려던 말이 ~인가요"를 짐작과 함께 묻는다. 메모가 "뭔가 어색하다"처럼 막연할 때도 고치기 전에 한 가지를 묻는다. 의도가 글에 이미 분명하면 생략한다.
2. **고치기 종류 정하기**: 아래 표에서 고른다.
3. **방안 2~3개**: 각 방안에 실제로 들어갈 문장 초안을 붙이고 하나를 추천한다.
4. **작성자가 고르거나 고쳐 준 대로** 반영한다. 작성자가 자기 말로 의도를 풀어 주면 그 표현과 예시를 최대한 그대로 살린다.
5. **고친 뒤 확인**: `flow-checks.md` 의 「고친 뒤 확인」을 돈다.
6. 다음 곳으로 넘어갈지 묻는다.

| 고치기 종류 | 뜻 |
|---|---|
| 조이기 | 되풀이·군말을 덜어 밀도를 높인다 |
| 늘리기 | 근거·사례·숨 쉴 틈을 더한다. 사례는 작성자가 준 것만 |
| 각도 바꾸기 | 말하려는 것은 그대로, 보는 각도나 강조를 바꾼다 |
| 날 세우기 | 주장을 더 정확하게 한다 |
| 순서 바꾸기 | 흐름이나 힘을 위해 순서를 바꾼다 |
| 문체 맞추기 | 그 글의 문체(`CLAUDE.md` 「문체」)에서 벗어난 곳을 되돌린다 |
| 다리 놓기 | 앞뒤 구간을 잇는다 |
| 아끼는 것 빼기 | 작성자가 좋아하지만 흐름 밖에 있는 것을 뺀다 |

## 되묻는 경우

작성자의 요청이 글을 해칠 때는 그대로 하지 않고 이유와 대안을 낸다.

- 단순하게 해 달라는데 그 복잡함이 주장의 근거일 때: "더 단순하게 말고 더 분명하게 해 보겠다"고 제안한다.
- 기획서의 "넣지 않을 것"과 부딪힐 때: 부딪힌다고 말하고, 그것을 피하는 방안을 낸다.
- 문체가 바뀔 때: "이렇게 고치면 합니다체 기준 글보다 거칠어진다. 의도한 것인가"를 묻는다.

## 보고 형식

```
고치기 종류:
고친 문단: (바뀐 본문)
바꾼 것: (한두 문장)
기획서·CLAUDE.md 확인: (주장·제약·문체를 지켰는지)
```
