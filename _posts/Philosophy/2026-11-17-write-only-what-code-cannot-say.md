저는 오래전부터 주석을 줄이자고 말하고 다녔습니다.
함수가 하는 일을 한 번 더 적은 주석이 리뷰어를 피곤하게 만드는 일이 많았기 때문입니다.

요즘 이 말이 조금 다르게 들립니다.
코드를 읽는 쪽에 사람만 있지 않게 되었기 때문입니다.
AI 에이전트가 코드를 읽고 그 코드를 본보기 삼아 다음 코드를 씁니다.

> "무엇을 문장으로 남기고, 무엇을 코드에 맡겨야 하나."

## 주석은 코드를 따라가지 못한다

제가 주석을 줄이자고 한 가장 큰 이유는 SSOT 입니다.
Single Source of Truth, 하나의 사실은 한 곳에만 둔다는 원칙입니다.
리뷰어가 피곤한 것은 겉으로 드러난 일이고, 뿌리는 여기에 있습니다.

코드는 시간이 지나면 유기물처럼 바뀝니다.
요구 사항이 바뀌고 버그가 고쳐지고 구조가 정리됩니다.
그런데 그 코드를 설명하던 주석은 저절로 바뀌지 않습니다.

같은 사실이 코드와 주석 두 곳에 있으면 언젠가 둘은 다른 말을 합니다.
그때 읽는 사람은 어느 쪽을 믿어야 할지 모릅니다.
코드는 실행되니 적어도 지금의 동작을 말하지만 주석은 아무도 검사하지 않습니다.

그래서 저는 최소한의 주석만 남기자는 쪽입니다.
문제는 무엇을 남기고 무엇을 지우느냐입니다.

## 두 가지 기준

코드베이스가 사실과 다른 말을 하는 문제는 주석에만 있지 않습니다.
쓰이지 않는 채 남겨 둔 코드도 같은 문제를 만듭니다.
그래서 기준은 두 가지입니다.
이번 버전에 쓰이지 않는 코드는 지우고 주석은 코드가 말하지 못하는 것만 씁니다.

### 안 쓰는 코드는 지운다

어느 순간부터 저는 다음 버전에 쓰일 게 확실한 코드라도, 이번 버전에 쓰이지 않으면 지웁니다.

남겨 둔 코드는 그 자체로 하나의 주장이 됩니다.
"이 코드는 쓰이고 있다"는 주장입니다.
다음에 읽는 쪽은 그 코드를 지금 쓰는 패턴으로 받아들입니다.
이것도 SSOT 의 문제입니다.
코드베이스가 말하는 사실과 실제로 돌아가는 사실이 달라집니다.

지운 코드의 기억은 코드가 아니라 git 에 남아 있습니다.
예전에는 지운 코드가 다시 필요해지면 내일의 제가 더 좋은 코드를 만들어 낼 거라고 믿었습니다.
요즘은 믿음 대신 AI 가 그때 로직을 찾아오게 합니다.

1. **떠올린다**: AI 에게 git 커밋을 뒤지게 해서 그때 로직을 어떻게 짰는지 상기함
2. **비교한다**: AI 와 협의해 더 좋은 방법을 찾거나, 바뀐 코드와 예전 코드를 같이 쓸 수 없는지 판단함
3. **새로 만든다**: 지금 코드에 맞는 최적의 방식을 만듦

### 주석은 비즈니스의 "왜"만 남긴다

그렇다고 주석을 아예 쓰지 않는 것은 아닙니다.
저는 주석으로 함수를 설명하지 않습니다.
로직이 아니라 비즈니스에 대해서만 씁니다.

예를 들어 "X요일 오후 Y시부터 Z시까지 이벤트 팝업을 띄운다"는 코드가 있다고 하겠습니다.
요일과 시간을 비교하는 로직은 코드가 그대로 보여 줍니다.
하지만 왜 하필 X요일인지는 코드로 표현할 수 없습니다.
그건 기획과 비즈니스의 영역입니다.
이런 것이 주석으로 남길 만한 내용입니다.

이 주석은 SSOT 와도 부딪히지 않습니다.
왜 X요일인지는 코드에는 없는 사실이라, 코드와 주석이 같은 사실을 두 번 말하지 않습니다.

| | 남기는 주석 | 쓰지 않는 주석 |
|---|---|---|
| 내용 | 왜 X요일인지 같은 비즈니스 결정 | 함수가 무엇을 하는지 다시 설명 |
| 출처 | 기획·비즈니스 | 코드 자체 |
| 코드 로직이 바뀌면 | 결정이 그대로면 여전히 맞음 | 코드와 어긋남 |

두 기준은 결국 한 문장으로 모입니다.
**코드로 표현할 수 있는 것은 코드가 말하게 하고, 코드로 표현할 수 없는 것만 문장으로 남깁니다.**

## 팀원이 에이전트가 됐다

두 기준은 모두 다음에 이 코드를 읽을 팀원을 위한 것입니다.
팀원이 바뀌어도 코드는 읽혀야 하고 오류는 구조가 막아야 합니다.
안 쓰는 코드를 지우는 것도, 주석을 비즈니스의 "왜"로 좁히는 것도 코드가 스스로 읽히게 하려는 일입니다.
읽히는 데서 더 나아가 실수까지 막는 일은 린트 같은 정적 분석이 맡습니다.

그런데 그 팀원이 이제는 에이전트가 된 것 같습니다.

Lauren Tan(poteto)의 발표 「[All Code Is Slop (Except Mine)](https://www.youtube.com/watch?v=O_zcc6Xl12g)」이 이 이야기를 합니다.
2026-11-14 에 AI Engineer 채널에 공개된 발표입니다.
slop 은 AI 가 대충 찍어 낸 질 낮은 결과물을 가리키는 말입니다.

발표자는 코드베이스를 정원에 비유합니다.
우회 코드(고치지 않고 돌아가게만 만든 코드), 안티패턴, 기술 부채가 남아 있으면 다음 에이전트가 그것을 패턴으로 알고 복제합니다.
그래서 에이전트를 믿으려면 먼저 환경에 투자해야 한다고 말합니다.

투자 순서도 제시합니다.

1. **코드 자체**: API 설계와 아키텍처
2. **린트·타입·테스트**: 기계가 검사하는 규칙
3. **런타임 검증·정형 검증**: 실제로 돌려 보거나 수학적으로 증명하는 검사
4. **문장**: 규칙, 스킬, AGENTS.md·CLAUDE.md(에이전트에게 주는 지침 문서). 마지막에 얇게 둠

주석에 대한 이야기도 있습니다.
발표자의 팀은 제품 코드에서 주석의 99% 를 금지했습니다.
에이전트가 주석으로 우회 코드를 정당화했고 다음 에이전트가 그 주석을 철칙처럼 따랐기 때문입니다.
주석은 낡고 강제할 수 없다는 것이 발표자의 설명입니다.

이 발표가 모든 팀의 답은 아니겠지만 제가 오래 해 온 말과 같은 쪽을 가리킵니다.
주석을 다루는 방식은 조금 갈리는데, 그 이야기는 마지막에 다시 하겠습니다.

예전과 달라진 것은 읽는 쪽입니다.
사람 리뷰어는 낡은 주석을 의심하고 코드를 확인하지만, 에이전트는 적힌 주석을 그대로 믿고 그 위에 코드를 쌓습니다.

## 문장 말고 구조로 막는다

발표의 또 다른 축은 검사입니다.
코드가 읽히는 데서 더 나아가, 오류를 구조로 막는 쪽입니다.
에이전트가 틀리면 AGENTS.md 에 줄을 더하지 말고 결정론적 검사로 바꾸라는 것입니다.
결정론적 검사는 린트나 타입 검사처럼 같은 코드에 언제나 같은 결과를 내는 검사입니다.

발표자가 든 사례는 둘입니다.

- React 의 `useEffect` 를 제품 코드에서 금지함
- Electron 앱의 main(바탕에서 도는 프로세스)과 renderer(화면을 그리는 프로세스)를 최상위 폴더로 나누고, 서로 import 하는 것을 린트로 막음

두 번째 사례는 제가 앱 아키텍처에서 중요하게 생각하는 것과 같습니다.
앱 아키텍처의 핵심은 의존성을 경계로 모듈끼리 엮이지 않게 하는 것입니다.
그 경계가 AI 의 import 실수를 막는 바리케이드가 됩니다.
"이 레이어에서 저 레이어를 부르지 말라"는 문장은 에이전트가 놓칠 수 있습니다.
경계를 넘는 import 가 빌드에서 걸리면 놓칠 수가 없습니다.
그래서 저는 **아키텍처도 크게 보면 하나의 린트**라고 봅니다.

| | 문장으로 막기 | 구조로 막기 |
|---|---|---|
| 형태 | 지침 문서, 주석 | 린트, 타입, 의존성 경계 |
| 어겼을 때 | 아무 일도 없음 | 검사가 실패함 |
| 시간이 지나면 | 코드와 어긋남 | 어긋나면 검사가 먼저 알려 줌 |

발표자 팀은 검증에도 크게 투자합니다.
토큰 대부분을 검증에 쓰고, 리뷰도 영상, 스크린샷, 정형 검증 같은 검증 결과물로 합니다.
그 결과로 한 달에 PR 11,000 건을 냈고, 되돌린 비율은 약 0.5% 였다고 말합니다.
앱 성능도 오히려 좋아졌다고 합니다.
발표자 본인의 주장이고 저는 이 수치를 확인하지 않았습니다.

그렇다고 구조가 잡히면 에이전트가 slop 을 만들지 않게 된다는 말은 아닙니다.
다만 slop 을 만들 틈이 줄어들고 만들어도 검사가 먼저 알아챌 가능성이 커집니다.

## CLAUDE.md 도 주석이다

이 생각을 따라가면 하나가 더 보입니다.
CLAUDE.md 나 AGENTS.md 같은 지침 문서도 에이전트를 위한 주석입니다.
코드 밖에서 코드에 대해 말하는 문장이라는 점이 같습니다.
앞에서 발표가 지침에 줄을 더하지 말라고 했다면 여기서는 이미 있는 줄을 빼는 이야기입니다.

주석을 줄인 이유는 코드와 어긋나기 때문이었습니다.
지침 문서에는 이유가 하나 더 붙습니다.
읽는 쪽인 모델이 점점 많은 것을 스스로 알게 된다는 것입니다.
그래서 에이전트를 쓰면서 모델이 알아서 하는 일을 설명한 지침은 시간이 지날수록 의미가 없어진다고 느낍니다.

2026-11-16 에 제 개인 지식 저장소의 AGENTS.md 를 164줄에서 43줄로 줄였습니다.
지금 쓰는 모델(Anthropic 의 Opus 5.5)은 이렇게 자세히 적지 않아도 다 해 주기 때문입니다.
모델이 알아서 하는 일을 설명한 줄을 빼고 모델이 스스로 알 수 없는 사실만 남겼습니다.

지우면서 본 줄 중에 이런 뜻의 줄이 있었습니다.
"문서를 남기면 커밋하고 push 한다. 안 하면 다른 머신 세션이 낡은 규칙을 읽는다."
이 줄에도 "왜"가 들어 있지만 X요일의 "왜"와는 다릅니다.
X요일의 이유는 코드에도 모델에게도 없는 사실입니다.
push 하지 않으면 다른 곳에서 바뀐 내용을 볼 수 없습니다.
이것은 git 의 동작이고 모델이 이미 아는 상식입니다.
저는 이 이유를 보고 당연한 이야기를 왜 넣었나 싶었습니다.
그래서 커밋하고 push 하라는 규칙은 남기고 "안 하면…" 하는 이유 부분만 지웠습니다.
규칙은 이 저장소에서 정한 일이라 모델이 스스로 알 수 없습니다.

주석에서 함수를 다시 설명하는 문장을 지운 것과 같은 일입니다.
함수가 하는 일은 코드가 이미 말하고 push 하는 이유는 모델이 이미 압니다.
원칙은 같습니다.
읽는 쪽이 이미 알 수 있는 것은 다시 적지 않습니다.
달라진 것은 읽는 쪽이 모델이 되면서 "이미 알 수 있는 것"의 범위가 넓어졌다는 점입니다.

에이전트는 적힌 것을 낡았든 군더더기든 그대로 따르고, 동시에 적지 않은 것도 많이 압니다.
두 성질 모두 문장을 줄이라는 쪽을 가리킵니다.

### 스킬과 플러그인도 같은 길로

하는 법을 적은 문장은 지침 문서에만 있지 않습니다.
에이전트에게 일하는 순서를 가르치는 스킬과, 특정 기술을 쓰는 법을 덧붙이는 플러그인도 같은 종류입니다.

예전에는 PR 올리기, 머지하기 같은 스킬을 직접 만들어 썼습니다.
작업을 하위 세션(따로 띄운 에이전트 세션)에 맡기는 스킬도 만들었습니다.
요즘은 이런 스킬이 점점 필요 없어지는 것 같습니다.

그래서 앞으로 스킬은 작업 흐름의 패턴을 정리하는 용도가 아니라, 그 사람만의 업무 흐름에만 쓰일 것 같습니다.
"이 일을 하고 나면 Slack 으로 알림을 보낸다" 같은 것입니다.
이것은 모델이 코드를 아무리 잘 읽어도 알 수 없습니다.
저도 그쪽으로 방향을 잡아 가고 있습니다.

플러그인도 비슷합니다.
Flutter·React·Swift 를 쓰는 법을 알려 주는 플러그인은 AI 가 그 기술을 가장 잘 쓰게 되면 붙일 필요가 없어질 것 같습니다.
시뮬레이터 조작이나 최신 문서 조회처럼 모델 밖과 연결해 주는 플러그인은 성격이 다릅니다.
모델이 아는 것이 아니라 모델이 닿지 못하는 곳이기 때문입니다.

## 금지가 아니라 기준

발표와 제 생각이 갈리는 곳은 주석입니다.
출발점이 다르기 때문입니다.

| | 발표의 규칙 | 제 규칙 |
|---|---|---|
| 출발점 | 에이전트 | 비즈니스 |
| 주석을 보는 눈 | 에이전트가 우회 코드를 정당화하는 탈출구 | 기획의 "왜"가 코드 옆에 남는 유일한 자리 |
| 규칙의 모양 | 99% 금지 | 기획·비즈니스에서 온 이유만 남김 |

저는 금지가 아니라 "기획·비즈니스에서 온 이유만 남긴다"는 기준으로 거릅니다.
우회 코드를 변명하는 주석은 이 기준을 통과하지 못합니다.

앞에서 에이전트는 적힌 주석을 그대로 믿는다고 했습니다.
남는 주석이 기획의 결정뿐이라면 에이전트가 따라도 따라야 할 것만 남습니다.
그래서 이 기준은 읽는 쪽이 사람이든 에이전트든 바뀌지 않습니다.

정리하면 이렇습니다.

- **주석**: 함수를 다시 설명하지 않고 비즈니스의 "왜"만 남김
