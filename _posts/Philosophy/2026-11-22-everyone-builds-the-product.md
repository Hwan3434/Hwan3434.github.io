지난 글은 개발자가 코드 대신 하네스를 만든다는 이야기로 끝났습니다.
하네스는 AI 가 엉뚱한 쪽으로 가면 막히게 하고 막히면 길을 알려 주는 장치입니다.

예전에는 기획서가 나오면 디자이너가 화면을 그리고, 개발자가 만들고, QA 가 확인했습니다.
요즘은 이 순서가 흐트러지고 있습니다.
만드는 일이 개발자만의 일이 아니게 되었기 때문입니다.

> "누구나 만들 수 있게 되면, 팀에서 각자는 무엇을 하나."

> 4편은 기획자·디자이너·개발자·QA 가 앞으로 어떤 일을 하게 될지 따라갑니다.

## 기획서 대신 화면이 온다

요즘 제가 일하는 흐름은 이렇습니다.

1. **기획자가 화면을 만든다**: 대시보드 같은 화면을 HTML 목업으로 만들어 옴
2. **디자이너가 디자인 시스템을 만든다**: HTML 에 맞춰 디자인 시스템을 만들고 개선함
3. **개발자가 그 디자인 시스템으로 개발한다**: 앱 화면을 만들고 실제 데이터를 붙임

| | 예전 | 요즘 |
|---|---|---|
| 기획자가 넘기는 것 | 기획서 | HTML 목업 |
| 디자이너가 만드는 것 | 화면마다 그린 시안 | HTML 에 맞춘 디자인 시스템 |
| 개발자가 보고 만드는 것 | 디자이너의 시안 | 디자인 시스템 |

다만 기획자의 HTML 이 그대로 나가지는 않습니다.
HTML 에는 데이터가 빠져 있습니다.
실제 데이터를 붙여 상용 앱에 올리는 일은 앱 개발자가 합니다.

## 경계가 흐려지는 팀

우리 팀만의 일은 아닙니다.
Anthropic 에서 Claude Code 의 엔지니어링을 이끄는 Fiona Fung 은 "요즘 우리 PM 들은 코드를 많이 씁니다"라고 말합니다([글](https://claude.com/resources/articles/running-an-ai-native-engineering-org), 2026-06-03).

| | 예전 | 지금 |
|---|---|---|
| 팀 구성 | 역할이 고정됨. 개발자는 코드, PM 은 기획, 디자이너는 디자인 | 역할이 흐려짐. PM 은 프로토타입을 만들고 개발자는 디자인과 맥락을 맡음 |

같은 회사의 PM 인 Jess Yan 은 해야 할 일이 분명해지면 그 일을 하는 에이전트를 Claude Code 로 직접 만들어 배포한다고 씁니다([글](https://claude.com/resources/articles/product-management-on-the-ai-exponential), 2026-04-29).

1편에서 저는 기획자가 개발을 배우는 것이 가장 낫다고 썼습니다.
그때는 전망이었는데 지금은 어떤 팀에서 PM 이 만든 것이 그대로 나갑니다.

그렇다면 우리 팀에서는 마지막 단계가 왜 아직 개발자의 몫일까요.

## 하네스가 있으면 누가 만들어도 같다

제 답은 하네스입니다.

요즘 저는 하고 싶은 것을 AI 에게 넘기면 AI 가 다 합니다.
제가 간간이 보는 것은 jank(화면이 버벅이며 밀린 프레임), 메모리, 불필요한 함수나 로직 정도입니다.
아키텍처 패턴은 하네스가 이미 잡아 줍니다.

하네스는 누가 AI 에게 시켰든 똑같이 막습니다.
경계를 넘는 import 는 개발자가 시켰든 기획자가 시켰든 같은 검사에서 걸립니다.

**하네스가 잘 만들어진 프로젝트에서는 기획자와 개발자가 같은 품질의 코드를 만듭니다.**

저는 이것이 지금도 가능하다고 봅니다.
다만 기획자에게 직접 시켜 본 적은 없습니다.
그렇게 해 달라고 한 기획자도 없었고 함께 일한 기획자들은 개발을 잘 모르셨습니다.
그래서 이 부분은 제 경험에서 나온 전망입니다.

## 하네스가 잡지 못하는 것

코드 품질이 같으면 제품도 같아질까요.

| | 예 | 같게 만드는 장치 |
|---|---|---|
| 코드 품질 | 구조, 의존성 경계 | 하네스 |
| 보이는 모양 | 색, 글꼴, 간격, 컴포넌트 | 디자인 시스템 |
| UX | 레이아웃, 화면의 흐름 | 없음 |

화면을 어떻게 배치하고 사용자를 어떤 흐름으로 이끌지는 검사로 막을 수 없습니다.
저는 기획자가 레이아웃을 배치하면 UX 가 상당히 딱딱해질 것 같습니다.
Fiona Fung 도 제품 감각과 취향에는 PM 과 디자이너가 여전히 필요하다고 말합니다.

그래서 기획자가 와이어프레임(화면에 무엇을 어디에 둘지 잡은 뼈대)까지 만드는 지금의 흐름은 오래가지 않을 것 같습니다.
기획자는 기능을 설계해 목록을 넘기고, 화면은 디자이너가 디자인 시스템 위에서 잡는 쪽이 자연스럽습니다.
지금의 흐름은 과도기의 모습입니다.

## 각자에게 남는 일

AI 와 하네스가 좋아질수록 서로의 영역에 들어가는 일은 잦아질 것 같습니다.
그래도 역할이 하나로 합쳐지지는 않는다고 봅니다.
만들어 보는 일은 섞이고 책임지는 영역은 오히려 또렷해집니다.

| 역할 | 과도기(지금) | 그 뒤 |
|---|---|---|
| 기획자 | HTML 목업과 와이어프레임까지 만듦 | 기능을 설계하고 기능 목록을 넘김 |
| 디자이너 | 받은 HTML 에 맞춰 디자인 시스템을 만듦 | UI/UX, 레이아웃, 와이어프레임, 디자인 시스템을 맡음 |
| 개발자 | 디자인 시스템으로 개발하고 데이터를 붙임 | 하네스를 만듦 |
| QA | 손으로 확인함 | 무엇을 자동으로 검사할지 정함 |

개발자 줄은 조금 풀어 둡니다.
제가 간간이 보는 jank 나 메모리도 사실 CI(코드가 올라올 때마다 자동으로 빌드하고 검사하는 장치)에서 하네스로 잡을 수 있습니다.
다만 그런 하네스를 만드는 일은 아직 개발을 모르면 하기 어렵습니다.
AI 가 더 좋아지면 이것도 스스로 하겠지만 아직은 아닙니다.
상용 앱에 올리려면 성능과 구조가 지켜져야 합니다.
**그것을 지키는 하네스를 지금은 개발자만 만들 수 있기 때문에 마지막 단계가 개발자의 몫입니다.**

## 과도기는 2~5년

저는 지금부터 2~5년을 과도기로 봅니다.
그 안에 90% 넘는 회사가 이렇게 바뀔 거라고 예측합니다.
상용 앱 개발을 기준으로 한, 확정이 아닌 추측입니다.

근거는 제 경험입니다.
1년 전에는 IDE 가 개발의 기본이었습니다.
최근 3개월 동안은 IDE 를 연 기억이 거의 없습니다.

모두가 같은 도구로 같은 품질의 코드를 만들면 코드로는 제품이 갈리지 않습니다.
성공을 가르는 것은 그 제품이 고객의 문제를 해결하는 데 얼마나 결정적이냐입니다.
그리고 이것은 결국 사업의 목표에 얼마나 비전이 있느냐로 모입니다.

그러면 무엇을 만들지는 누가 정할까요.
지금은 기획자가 정합니다.
앱의 비즈니스 가치가 분명하다면 그 가치를 키우고 고도화하는 쪽으로 갈 것입니다.
다만 그 방식을 모두가 같이 협의한다면 그것은 또 하나의 병목입니다.
솔직히 이 경계가 어떻게 될지는 아직 모르겠습니다.

정리하면 이렇습니다.

- **하네스**: 잘 갖춰지면 누가 만들어도 같은 품질의 코드가 나옴. 그 하네스는 지금은 개발자가 만듦
- **하네스 밖**: 레이아웃과 화면의 흐름 같은 UX 는 디자이너의 몫으로 남음
- **과도기**: 기획자가 화면까지 만드는 지금의 흐름. 앞으로 2~5년
- **성공의 척도**: 고객의 문제를 얼마나 결정적으로 해결하느냐. 결국 사업 목표의 비전
- **남은 물음**: 무엇을 만들지 누가 정할지

만드는 일은 모두에게 열립니다.
각자에게는 무엇을 만들지, 무엇을 통과시킬지 정하는 일이 남습니다.

다음 글에서는 이 흐름의 그늘을 보려 합니다.
하네스와 가이드가 표준으로 굳으면, 모두가 같은 구조로 만든 제품은 서로 닮아 가지 않을까 하는 걱정입니다.
